# 知账 · Track 02 项目方案 V2

2026-09-17。替代 V1 中的赛道及交付裁剪建议；实现状态以《生产交付进度》为准。本稿不授权资金转移。参考文件中的“已确认”只代表该文件的叙述，不自动成为本项目约束。

## 产品定位

知账是一款把自动记账、可信关系中的私密评账和有依据的 AI 消费复盘连接起来的 Android 应用。先帮助用户知道钱如何花掉，再帮助他们理解和调整消费。面向 Track 02，拟探索从消费记录到用户确认的链上分账结算；具体支付模式仍待确定。

首批服务两至五人的真实关系小圈子，如朋友、伴侣、合租伙伴。日常人民币账本不要求钱包，链上支付作为可选的新业务域。没有用户增长、留存、节省金额或收入的已核验指标，本阶段以验证闭环为目标。

## 如何吸收参考方案

| 参考内容 | 本项目采用方式 |
|---|---|
| 互评账单、我的反馈、排行榜、关系管理 | 保留四个入口，接入原 App；不新建社交产品 |
| 关注、互关、单向授权及申请 | 保留，关注不是账单权限；后端统一判断范围 |
| 夯/拉、主评、私密回复和历史 | 保留，评价者之间隔离；主人可读自己的全部反馈 |
| 首页票数和文字圆点 | 接入原账单，不把首页改成公共动态流 |
| 日/月/年全站与好友榜 | 保留完整目标；不是财富认证，不与奖金挂钩 |
| 默认公开关系和准确结余 | 调整为隐私优先、明确加入，不自动公开老用户 |
| AI 日/月复盘 | 放在原 AI 页；仅结束周期，事实、朋友观点、AI 建议分开 |
| 评论默认可送 AI | 独立记录作者同意与主人使用同意；双方条件满足才纳入 |
| 通知与举报 | 保留；系统推送是待接入的独立能力，不等同支付通知监听 |
| 不转移资金 | 原记账/社群域继续保持；支付候选方案需另行确认，不能默默改变边界 |

V1 中“只做好友月榜、后置申请/恢复”的缩减不再作为完整交付范围；原文的撤回、审核、留档与删除规则需落到权限和保留策略，而不是永久保存所有私密内容。

## 账务与隐私必须贯穿全链路

- 期间现金结余＝普通收入＋当期退款流入－普通支出。内部转账和调账单列，未确认条目标出缺口。人民币与链上资产分别统计。
- 金额由服务器定点计算，AI 不重新做算术。没有历史预算依据时不推断当期超支。
- 评账只开放类型、金额、分类、时间；禁止额外下发商户、备注、原通知、发票或邮箱材料。
- 每次读取、写入、通知和深链重查当前授权。撤权、拉黑、删除、违规隐藏不能通过旧缓存或旧报告绕过。
- 编辑使历史报告标记来源变化；撤回/隐藏等隐私事件触发失效，恢复内容不会自动恢复旧报告。
- 排行使用统一 UTC+8 周期、封榜与当前隐私过滤；结余不是银行余额或净资产。

## Track 02 候选：消费后的分账结算

**此节为供选择的产品建议，未实现、未批准执行付款。** 用一个清晰的支付故事补足赛道契合度，而不是把报告哈希改名为支付。

示例：朋友聚餐后，记账人主动选取一笔账单并新建分账草案。AI 整理参与者和分摊建议；服务端计算份额。各方核对用途、币种、金额、收款地址和网络后自行签名。Monad 结算结果回写为独立链上记录，完成对账。

### 产品规则

1. 评账授权不等于付款授权。收到分账邀请也不会触发扣款。
2. 支付确认页单独展示网络、代币合约、原始单位/显示精度、份额、收款地址和预计网络费。AI 不持有私钥、不自行换收款地址。
3. 演示只使用明确标记的测试资产，不把 CNY 金额原样当成稳定币数量。首版不自动换汇；用户明确选择资产数量，人民币原账保留关联。
4. 每个结算意图独立 ID，校验参与者和金额总和；部分支付逐份记录，重复确认不重复入账。链上付款不能靠删除账单撤回，退款需单独签名。
5. 状态为草案、待确认、待签名、已提交、已确认或失败；拒签、链错误、超时保持可解释状态。收到哈希不等于成功，需核对 receipt、事件、资产及收款方。
6. 链上结算回写和原支付通知建立关联，避免一次经济事件记两次；没有可靠关联时标待核对，不自动吞掉条目。
7. 链上只出现支付所需信息，私密评论与通知原文不上传；签名前解释公开地址/金额带来的可关联性。

### 链上为何有用

参与者可用各自钱包结算并独立查看交易结果，知账无需保存私钥或维护托管余额；可验证的结算结果为分账对账提供依据。Monad 的具体成本与确认体验必须通过部署实测，不声称其他 EVM 网络无法实现。

如果最终选择有限授权自动支付，需要另做额度、有效期、接收方白名单、撤销、重放防护与执行审计设计，不能沿用“每次人工签名”的验收。未确定前继续完善不涉及资金的社群与复盘。

## 工程落点

保持 React Native + NestJS 模块化单体 + Prisma/PostgreSQL。复用现有 User/Bill、JWT 和模型适配器，不复制用户账本。

```text
Android 通知 → 解析/原文隔离归档 → Bill → LedgerService
                                        ├─ 首页 / 统计 / 预算
User → SocialAccessService → 私密线程 ───┤
                                        ├─ 排行快照
                                        └─ 复盘证据 → 作业 → 模型 → 私有报告

候选支付：用户选账单 → 分账草案 → 独立确认 → 钱包签名
          → Monad → receipt 校验 → 结算对账 → 关联账单
```

支付若获采用，新建独立 payments 域，区分 SettlementIntent、ParticipantShare、PaymentAttempt、ChainReceipt；账单关联可空，账单删除不能删除结算审计。生产密钥不进入客户端、代码或路演文件。具体钱包/RPC/代币/合约选型在场景确定后依据官方文档确认。

## 交付与验收

1. 完成现有社群/复盘全链路：真实模型、远程推送、真机跨账号、内容保留策略。
2. 确定一个支付场景，再实现测试网真实成功、拒签/失败、重复请求、错链和对账闭环。
3. 演练增量迁移与恢复；恢复生产连接后按批发布并线上验证，移动端每批递增版本。
4. 路演固定使用合成账号、标明环境与版本。已有产品、本次新增、本地验证和计划四种状态分别表述。

通过标准：B/C 互不可见；撤权后深链失效；AI 数字和依据可核对；账单/退款/互转无重复；未确认支付不计成功；真实链记录与账本关联一致。真实模型与链路未完成时，用设计示意替代并明确标注。

试用指标：邀请接受率、完整复盘成功率、引用正确率、次周复盘返回率；支付采纳后再测结算完成率、重复入账率、确认耗时和成本。当前不填写未经实测的数值。
