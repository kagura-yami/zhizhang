# 举报审核接口与验证

更新：2026-09-16。本批实现后端和管理端；移动端举报确认界面、通知投递、AI 消费端过滤及生产发布尚未完成。

## 用户接口

- `POST /review-reports/threads/:threadId/messages/:messageId`：需要用户 JWT、当前线程访问权限，不能举报自己。请求包括 `expectedRevision`、`reason`（1–1000 字符且非空白）、`acceptDisclosure: true` 和 `disclosureVersion: "2026-09-16"`。
- 同一人举报同一文字同一版本幂等；旧版本返回 409。举报本身不隐藏文字，不自动认定违规。
- `GET /review-reports?page=1&pageSize=20`：只返回自己的举报状态、原因和处理说明，不返回审核证据。

移动端提交前必须明确说明并要求确认：会向管理员披露该账单主人与该评价者之间的整条私密线程及历史文字版本。不能只写“提交举报”，也不能默认勾选同意。该界面尚待实现。

## 管理接口和界面

管理端新增“举报审核”入口，支持状态筛选、分页、目标文字标识、上下文、版本展开、处理说明和审核结论。窄屏改为纵向记录，避免操作按钮被横向表格挤出。

- `GET /admin-api/moderation`：分页查询，`status` 可为 `pending/upheld/dismissed`。
- `GET /admin-api/moderation/:id/evidence`：分页读取举报时的留档证据，每次读取写入管理员审计。证据不包含其他评价者线程或账单备注、原始通知等业务字段。
- `POST /admin-api/moderation/:id/decision`：`status` 为 `upheld/dismissed`，`reason` 为必填处理说明。普通用户 JWT 不可访问。最终处理只允许一次；相同结论和说明的重试幂等，不同结论返回 409。

举报时在权限锁和事务内冻结同一线程的文字与历史版本。之后修改或删除原文不覆盖证据。原账户或线程删除时外键置空，证据保留用于审核；具体保留期限、删除策略和用户披露需在生产上线前补齐，当前没有自动清理任务。

确认违规后隐藏目标文字当前版本和全部历史版本：普通详情返回空正文，历史接口拒绝读取，作者不能自行恢复。票数不变，其他回复可继续。管理员仍可读取专用证据接口。驳回举报不隐藏文字。

处理结果写入 `SocialInboxEvent`：举报人收到结果，成立时作者也收到；重试不会重复生成事件。这里只完成持久化，未接入系统推送或用户端未读列表。后续 AI/导出必须过滤 `hidden`，不能绕过普通阅读约束。
